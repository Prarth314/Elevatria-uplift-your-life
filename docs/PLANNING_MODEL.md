# Planning model and guarantees

This is the contract for the active local planner, not the retained prototype screens. See [engineering evidence](ENGINEERING_EVIDENCE.md) for verification scope.

| Concept | Semantics |
| --- | --- |
| Deadline | A goal has one inclusive calendar target date in the planning timezone. Every task inherits it. There are no task-level deadlines, release dates or due-time fields. Earlier goal dates are supported, including past dates with visibly unplaced work. |
| Effort | `Task.minutes` is an integer total estimate, 5–480 minutes. An unfinished task schedules the full estimate. There is no actual-time log or partial completion. Split sessions allocate the estimate; they do not consume it simply by elapsing. |
| Complete/reopen | Explicit user assertions only. Complete excludes all estimated effort from future scheduling; reopening restores the full estimate. Historical completion may be recorded out of prerequisite order. Reopening a parent does not silently undo a completed child. |
| Prerequisites | Distinct existing task IDs, including across goals. Cycles, self references and dangling references are invalid. An unfinished child starts only after every unfinished parent is fully allocated; recorded-complete parents impose no future work. Parent completion is an assertion, not proof of chronology. Remove references before deleting prerequisites. |
| Availability | One shared set of non-overlapping recurring same-day windows across all goals. Fixed dated commitments subtract from these windows; overlapping commitments naturally union. Separate windows can touch. |
| Budgets | Each goal has a 0.5–80 hour **cap**, not reserved availability. Weeks run Monday through Sunday in the planning timezone, with no proration or rollover. Total competing goals cannot exceed shared windows. |
| Sessions/breaks | Maximum 15–120 minutes; minimum allocation normally 15 minutes, except a task's entire remaining fragment may be shorter. Required gap of 0–60 minutes between **all task allocations**, across goals. Commitments themselves do not require extra breaks. Tasks may split across days/weeks. |
| Time | Horizon includes today and the next horizon−1 planning dates, at most 56 days. Start is rounded up to the next UTC minute. IANA timezone determines wall windows, dates, deadlines and weeks. Instants are stored as UTC ISO strings. |
| DST | Nonexistent boundary times skip a work window with a warning; a commitment with an invalid boundary blocks that window's day conservatively. Repeated boundaries choose the earlier occurrence. Windows spanning a clock change use elapsed time between those boundaries, so wall and elapsed duration may differ. |
| Free-text constraints | Notes for the person planning. They are not parsed, optimized or enforced. Use structured availability, commitments, budgets, prerequisites and dates for hard constraints. |
| Progress | Completed estimated minutes / all estimated minutes, rounded to a percentage. Editing estimates changes the weighting. This is neither measured productivity nor likelihood of success. |
| Accepted/proposed | Accepted is the last explicitly approved snapshot. Proposals/scenarios/recovery drafts are transient React state; reload discards them and session-only undo. Acceptance reruns revision, future-start and invariant checks before the validated save boundary. A storage error can leave acceptance in memory only; save status and export remain available. |
| Staleness | Goal changes (including text, estimates, completion, order, edges, caps and dates) or any settings change alter the fingerprint. Inspiration alone does not alter it. A fingerprint is a reproducible change detector, not cryptographic identity. Existing accepted work remains reference data, and stale Calendar export is blocked. |
| History | At most ten prior accepted schedules, 4,096 sessions/version and 16,384 sessions across accepted/history. History stores allocations, not former goals or former settings. Old constraints cannot be reconstructed; UI avoids explaining old snapshots using current constraints. Undo retains a full previous board only during the current session and refuses to overwrite newer edits. |

## Solver decisions and explanations

The generator visits eligible tasks by earliest **goal** deadline, descending priority (default 2), then original flattened board order, then ID. It scans free intervals chronologically and consumes per-goal weekly budget. Completed tasks start in the processed set. A partially placed parent does not release its children.

The independent validator checks shape/resource bounds, real availability/commitments, time/duration, breaks/overlap, inherited deadline, weekly caps, complete effort accounting and dependency order. A per-repair closure caches only immutable availability for one creation clock. Each candidate still undergoes all checks; tests compare cached and fresh validators on altered schedules.

Recovery reserves requested whole-task allocations, runs the same generator around them, then considers up to 200 eligible whole-task replacements from the previous snapshot. Protected or retained work can differ from a fresh earliest-deadline result. Changed/past/partly missed/completed task allocations cannot be protected. Unprotected partially allocated tasks may move. Protection is for that proposal, not a persistent lock. The change summary counts exact task/start/end matches, changed tasks with allocations on both sides, and allocations for wholly new/removed tasks; it does not invent a one-to-one identity for resized/split sessions.

Placement details show facts from the resulting snapshot: containing window, effort, inherited deadline, cap, prerequisite completion/allocation ends and session/break settings. They are not an exact rejection trace or causal proof that an earlier time was impossible. Unplaced explanations distinguish a passed deadline or no free window before deadline within the horizon from work the heuristic did not place. A blocked prerequisite is a result of this run, not proof that every task ordering fails. Invalid input and worker resource failures use separate visible error messages.

A bounded exhaustive test enumerates equal 30-minute jobs over three slots, independently of production code. It finds all three feasible where current EDF places two: a late-deadline prerequisite needs to run before its earlier-deadline child while independent work can wait. This intentionally documents a limitation; it does not validate all general instances or establish optimal scheduling. No global optimality, infeasibility or minimum-disruption claim is made.

## Persistence and portability boundaries

One version-1 JSON document is written with a single `localStorage.setItem`; a thrown quota/write error leaves the previous saved document recoverable. No multi-key migration is performed. Unsupported/corrupt versions remain untouched; both working and original saved exports are available. Storage events block writes after external change; a raw-value comparison at the save boundary also catches writes before an event arrives. All current-app browser writes acquire the same origin-scoped Web Lock before comparison and replacement, including retries and explicit resets. This prevents two cooperating current-app tabs from both passing the comparison. Obsolete queued writes and writes superseded by account changes are discarded. Browsers without Web Locks keep changes in memory and show an export warning. Old app versions, extensions, DevTools, or unrelated code that bypass this lock cannot be coordinated; avoid mixing app versions during editing. Locks do not replace backups or guarantee hardware durability.

Imports validate strict schema, graph and aggregate limits, re-encode images, preview replacement and reject a preview if the board changed while reading/reviewing. Exports/imports preserve IDs, dependencies and schedule/history shapes. Shape-valid imported snapshots are not implicitly trusted as feasible; Calendar export validates the current accepted snapshot again. Stale history can legitimately reference deleted tasks.

ICS uses UTC instants, CRLF, escaped text, 75-octet UTF-8 folding and stable `taskID-occurrenceIndex` UIDs. Repeating an unchanged export keeps UIDs, and moving the same ordinal keeps its UID. Changing split count can leave old remote events; the file does not issue deletion/tombstone reconciliation or guarantee client update behavior. `ical.js` independently parses output in tests. No Google import/sync claim follows from file validity.

Account documents stay in memory and use explicit authenticated cloud operations; they never pass through the demo write adapter. Existing verified-identity, server ownership, optimistic revision, owner RPC, size/time bounds and SQL tests remain. Real OAuth callbacks and hosted two-account isolation are pending user-provided configuration.
